# STS、ECS 与 VPC 开发路线

[English](sts-ecs-vpc-path.md)

## 路线依据

- 用户于 2026-10-09 调整顺序：先完成 #60，再完成 ECS、VPC 验收，最后执行 #61 发布。
- 新路线替代原先首版只发布 STS 的安排；已有验收证据和历史决策继续保留。
- 继续使用固定的官方 Darabonba DSL、官方语义解析器、完整 IR、公共 Go 生成后端与运行时。
- 保持 Go 1.27、JSON v2、AWS 风格调用方式和阿里云原生协议语义。
- 收尾 STS 时不创建版本标签或发布。

## 执行顺序

1. 在最新已接受的 SDK 版本上完成 #60，记录实际验收者类型和任务结果；代理执行不能写成独立人工验收。
2. 完成 ECS #74 的明确范围验收：完整生成的 RPC 操作清单，以及已审核的分页、等待器、重试和消费者任务。
3. 完成 VPC #75 的明确范围验收：完整生成的 RPC 操作清单，以及已审核的分页、重试和消费者任务。
4. 必需产品门禁通过后再执行 #61，发布明确声明的范围，并检查同版本 pkg.go.dev 页面。

## 产品范围

- 当前固定基线生成四个 STS、283 个 ECS、296 个 VPC 操作。这是生成数量，不是真实调用覆盖。
- STS 包含四个操作、角色凭据与缓存、原生 Profile 组合，不添加分页器或 waiter。
- ECS 先验收 DescribeRegions、DescribeImages、DescribeInstances、DescribeInstanceStatus 的消费者契约，保留原生页码、token 和 InstanceRunningWaiter 语义。
- VPC 先验收 DescribeVpcs 及原生页码分页器，不凭空增加 token 接口或 waiter。
- 按完整 IR 审核能力策略。未列出的操作在重试和适配器层面仍为未审核；原始操作的发现不依赖逐 API 手写配置。
- 每个发现的操作都有记录，分别说明降低、生成、编译、独立测试和真实调用状态。不支持的协议形态必须说明原因，选中生成时在写入前失败。
- 执行前明确产品任务、必需验收项和范围外项；仅能编译不代表产品完成。
- #47/PR #48 是另一条 ECS/VPC 只读证据记录。合入前审核实际结果，不把空页和跳过的 waiter 检查当成真实翻页或状态迁移成功。
- #55 的续期、#60 的身份与来源升级演练、#68 的原生 OAuth 证据，在相关行为未改变时直接复用。
- 真实联邦身份、新协议、任意资源写入、全云覆盖和基准 #20 继续单独定义范围。

## 证据与 GitHub 管理

- 产品 issue 明确验收矩阵、依赖、验证方法和中英文文档要求。
- #61 依赖 #60 及两个产品验收 issue；#57 和 v0.1.0 milestone 在发布、索引完成前保持打开。
- 实际 GitHub 依赖图保持无环；父子关系不作为子项的阻塞依赖。
- 每个 issue 保留一个状态 label，并与 Project 状态同步。issue 和 PR 仅用英文。
- 人工使用体验与代理消费者测试分开记录，用户已选择代理验收完成 #60；可选人工体验另由 #76 跟踪，只有真实人工结果才能更新人工记录。
- 来源、运行时、策略和生成文件的修改继续采用 issue 驱动；中英文指南在同一变更更新。
